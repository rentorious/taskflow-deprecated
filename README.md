# Taskflow

Automated task triage and implementation from project management tools like ClickUp.

Taskflow is a Claude Code plugin that pulls tasks from your project management tool, classifies them, creates implementation plans, groups them into smart batches, and then implements each batch — complete with worktrees, tests, and PRs.

## Installation

```bash
claude plugins marketplace add github:rentorious/taskflow
claude plugins install taskflow@taskflow
```

After installing, restart Claude Code for the skills to become available.

## Quick Start

1. **Setup** — Run `/taskflow:setup` to generate `.claude/taskflow-config.json` for your project. The wizard auto-detects your codebase structure and walks you through connecting your project management tool.

2. **Triage** — Run `/taskflow:triage` to pull your assigned to-do tasks, classify them, create per-task implementation plans, and group them into batches.

3. **Report** — Run `/taskflow:report` at any point to open the report in your browser: what is waiting on you, what is ready to claim, what is in flight and what is blocked. It updates itself while implement sessions work.

4. **Implement** — Run `/taskflow:implement` to execute the next batch: creates a worktree, implements changes, runs checks, updates task statuses, and opens a PR.

5. **Clean** — Run `/taskflow:clean` when a cycle is done. It stops the report server and archives the index, batches, plans and attachments to `<output_dir>/archive/<cycle-date>/`, so the next triage starts from a blank slate. `--purge` deletes everything instead.

## Skills

| Skill | Command | Purpose |
|-------|---------|---------|
| Setup | `/taskflow:setup` | Interactive wizard to generate project config |
| Triage | `/taskflow:triage` | Fetch, classify, plan, and batch tasks |
| Implement | `/taskflow:implement` | Execute a batch: implement, verify, PR |
| Report | `/taskflow:report` | Live report grouped by what happens next, with an inbox of things that wait on you |
| Clean | `/taskflow:clean` | Archive (or `--purge`) the local state to start a fresh cycle |

## The report

`/taskflow:report` starts a small local server (Node 18.17+, no dependencies, `127.0.0.1` only) and prints its URL.

- **A queue grouped by what happens next.** Needs you, ready to start, in flight, pull request open, blocked, shipped and stale, not batched. "Ready to start" is exactly what `/taskflow:implement` would claim, in the order it would claim it; "Blocked" names the batches it waits on.
- **An inbox.** Questions for the client, provider writes that failed and must be pasted by hand, fixes to verify and close, and broken pipeline state such as a stale lock. Copy the text, tick the item off, and it moves to "waiting" or out of the way. Ticks live in `report-inbox.<slug>.json`; the report never writes pipeline state.
- **Answers, and a gate that reads them.** Triage writes one entry per question. You type what the client or a colleague said into the report, with who said it; either/or questions are one tap. A batch with an unanswered *blocking* question sits under Blocked, and `/taskflow:implement` will not start it: claiming goes through `scripts/taskflow.mjs claim`, which decides by exit code (`2` = questions open) and lists what is missing. There is no force flag; the way past a question is to drop it, with a reason. Implement reads the answers next to each plan. Answers live in `answers.json`, keyed by task rather than by cycle, so they survive `/taskflow:clean` and re-attach on the next triage.
- **The plan next to the queue.** Each batch opens with its command, branch, dependencies, time estimates, the per-task plans and screenshots.
- **Pull request state and leftover worktrees**, when `gh` and `git` are available. Without them the report still works.
- **Archives.** Every cycle archived by `/taskflow:clean` stays selectable, read-only.
- **A snapshot.** `/taskflow:report --snapshot` writes the whole report as one HTML file that opens without a server.

## Config Reference

The config file lives at `.claude/taskflow-config.json` in your project. It's generated by `/taskflow:setup` and consumed by the other skills.

| Field | Description |
|-------|-------------|
| `version` | Schema version (currently `1`) |
| `provider` | Project management tool (`"clickup"`) |
| `project_name` | Used for worktree naming |
| `clickup` | Provider-specific config (workspace, lists) |
| `areas` | Classification areas with paths and verification commands |
| `extra_areas` | Non-code classification areas (e.g., `"sendgrid"`, `"manual"`) |
| `branch_conventions` | Branch prefix mapping by task type |
| `output_dir` | Where state/plan files are written |
| `base_branch` | Branch to create worktrees from |
| `build_before_implement` | Commands to run in worktree before implementation |
| `install_command` | Dependency installation command |
| `full_lint` | Full-repo lint command |
| `full_typecheck` | Full-repo typecheck command |
| `provider_comments` | **Default `false`.** Post developer-voice comments back to the provider. See below |
| `provider_enrichment` | **Default `false`.** Rewrite task descriptions and link duplicate tasks in the provider. See below |
| `server` | Optional. `{ "url", "project" }` of a hosted dashboard your team runs (see `server/`). Then `taskflow push` mirrors the cycle there, answers are typed into that dashboard, and `taskflow claim` lets the server decide. The token is stored by `taskflow.mjs login <url>`, never in this file |

### Provider comments (off by default)

Taskflow used to write a developer-voice comment on every task — a clarification question during triage, a "here's what I changed + PR link" note during implement. That is now **disabled by default**, because comment volume is permanent provider-side storage and counts against free-plan quotas.

With `provider_comments` absent or `false`:

- No comments are posted, ever.
- Clarification questions for low-confidence tasks are still drafted — they land in the task's plan file under `## Open Question` and in the triage summary under **Low Confidence Tasks**, ready to paste manually.
- PR URLs still land in the batch file and the implement terminal summary; the PR body links every task.
- Status transitions (`to do` → `in progress` → `code review`) are unaffected.

To opt back in, set it in `.claude/taskflow-config.json`:

```json
"provider_comments": true
```

### Provider enrichment (off by default)

Triage used to rewrite each task's description with its findings and link duplicate tasks, unconditionally. The ticket is the client's document, so that is now **off by default** too. With `provider_enrichment` absent or `false`, what triage learned goes into the plan file's "What Needs to Change", duplicates are recorded in the index and the summary, and **the only thing taskflow writes to the provider is a task's status.** Set `"provider_enrichment": true` to opt back in; descriptions are then appended to, never replaced.

### The CLI

`scripts/taskflow.mjs` is what the skills call; it is handy in a terminal too. All commands take `--dir <output_dir>` (or find it from `.claude/taskflow-config.json` above the working directory) and `--dev-slug` when several developers share the directory.

```bash
node scripts/taskflow.mjs status              # what is next, and which answers are missing
node scripts/taskflow.mjs claim [batch-key]   # exit 0 claimed, 2 questions open, 3 locked, 5 dependency, 6 nothing, 7 complete
node scripts/taskflow.mjs release <batch-key> # give a claim back
node scripts/taskflow.mjs answers <batch-key> # rewrite answers/<task>.md after recording more answers
node scripts/taskflow.mjs questions <task-id> # JSON: exact wording and recorded answers, for triage to reuse
```

Hosted projects (a `server` block in the config) add `login <url>`, `push`, `archive` and `runner`:

```bash
node scripts/taskflow.mjs runner [--kinds implement,triage]   # run the jobs the hosted dashboard queues for this machine
```

The runner is the long-lived process on a developer's own machine. It takes the jobs the dashboard queues (**Start on my machine** on a ready batch, **Triage on my machine** on the Jobs page), runs the unmodified `claude` headless for each with the matching skill, and streams the session's log back. Questions the session would have asked in the terminal, and permissions the mode would have asked for, are routed to the dashboard by the plugin's mod and answered from a phone. Without `--kinds` it runs every kind it knows.

## Development

The plugin has no build step and no dependencies. The report's tests run on plain Node:

```bash
node --test "test/*.test.mjs"
```

To look at the report without a real project, write a synthetic cycle to disk and point a second server at it:

```bash
node test/fixtures/materialize.mjs kitchen-sink /tmp/taskflow-kitchen-sink
node scripts/report-server.mjs --dir /tmp/taskflow-kitchen-sink --port 3848 --no-pidfile
```

Fixtures are generated by code (`test/fixtures/specs.mjs`) and are entirely invented. This repository is public: never commit real task titles, provider ids, client names or pull request URLs.

### The hosted server (work in progress)

`server/` is a hosted version of the report, over Postgres. It is a separate npm package with one dependency (`pg`) and reuses `scripts/report/`; the plugin never needs it installed, and a test fails if anything under `scripts/` imports a package. It is nested on purpose: Claude Code runs `npm ci` for a plugin whose root holds a `package.json` and a lockfile.

People sign in with GitHub (no scopes asked) and are let in by invitation; the CLI uses a personal token. Without the four sign-in variables it starts only on a loopback address and refuses every write. Design, variables and status: `docs/specs/2026-09-18-hosted-dashboard-design.md` and the header of `server/config.mjs`.

Notifications to a phone are Web Push, with no dependency: set `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` (`node server/push.mjs generate-keys` prints a pair; `VAPID_SUBJECT` is an optional `mailto:` or `https:` contact) and the board shows **Notify me**. A browser that turns it on is told when a job needs an answer, when a job finishes or fails, when a pull request opens and when a machine pauses on its usage window. On an iPhone the dashboard has to be on the Home Screen first.

```bash
npm --prefix server ci
```

Its tests need a Postgres database whose name contains `test`. They create a throwaway schema per test file and drop it again. Put the URL in `server/.env.test` (ignored by git); without it the suite fails rather than skips.

```bash
createdb taskflow_test
echo 'TASKFLOW_TEST_DATABASE_URL=postgres://<user>:<password>@<host>:<port>/taskflow_test' > server/.env.test
npm --prefix server test
```

To look at it, push a fixture into a second database and start the server:

```bash
createdb taskflow_dev
printf 'DATABASE_URL=postgres://<user>:<password>@<host>:<port>/taskflow_dev\nPUBLIC_URL=http://127.0.0.1:3900\n' > server/.env.dev
node test/fixtures/materialize.mjs kitchen-sink /tmp/taskflow-kitchen-sink
node --env-file=server/.env.dev server/dev/seed.mjs --dir /tmp/taskflow-kitchen-sink --project demo --user dev
node --env-file=server/.env.dev server/main.mjs   # then open http://127.0.0.1:3900/p/demo/u/dev/
```
